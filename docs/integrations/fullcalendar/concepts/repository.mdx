The repository contract connects WebMCP calendar tools to your application's data layer.

Instead of writing to FullCalendar's internal memory or requiring a specific database, the FullCalendar WebMCP integration talks to an object implementing the [`CalendarEventRepository`](/integrations/fullcalendar/reference/calendar-event-repository) interface.

## The interface

```ts
export interface CalendarEventRepository {
  list(
    query?: CalendarEventQuery,
    options?: { signal?: AbortSignal },
  ): Promise<CalendarEvent[]>;

  get(
    id: string,
    options?: { signal?: AbortSignal },
  ): Promise<CalendarEvent | null>;

  create(
    input: CreateCalendarEventInput,
    options?: { signal?: AbortSignal },
  ): Promise<CalendarEvent>;

  update(
    id: string,
    input: UpdateCalendarEventInput,
    options?: { signal?: AbortSignal },
  ): Promise<CalendarEvent>;

  delete(
    id: string,
    options?: { signal?: AbortSignal },
  ): Promise<void>;
}
```

## Method breakdown

| Method | Plain language purpose |
|---|---|
| `list` | Read calendar events, optionally filtered by date range or title text. |
| `get` | Read a single calendar event by its stable event ID. |
| `create` | Persist a new event and return the saved event with its assigned ID. |
| `update` | Apply changes to an existing event and return the updated event. |
| `delete` | Permanently remove an event by ID. |

### Query filtering in `list`

The `list` method receives an optional [`CalendarEventQuery`](/integrations/fullcalendar/reference/types#calendareventquery):

```ts
export interface CalendarEventQuery {
  start?: string; // Inclusive ISO 8601 string
  end?: string;   // Exclusive ISO 8601 string
  text?: string;  // Case-insensitive title search substring
}
```

When an agent requests events for a specific week or searches for a meeting title, the integration passes those criteria directly to your `list` implementation.

### Cancellation with `AbortSignal`

Every repository method accepts an optional `{ signal?: AbortSignal }` parameter.

When a WebMCP request is aborted by the client browser or agent runtime, the integration signals cancellation. If your backend uses `fetch`, you can forward the signal directly:

```ts
async list(query, { signal } = {}) {
  const params = new URLSearchParams(query as Record<string, string>);
  const res = await fetch(`/api/events?${params}`, { signal });
  return res.json();
}
```

## Backend agnostic

The FullCalendar WebMCP integration works with any data source:

- REST APIs (`fetch`, Axios)
- Next.js Server Actions (see the [Next.js Guide](/integrations/fullcalendar/guides/nextjs))
- Supabase / PostgreSQL
- Prisma / Drizzle ORM
- GraphQL queries & mutations
- Browser `localStorage` (for prototypes)

For mapping custom domain entities to events, see the [Custom Event Models Guide](/integrations/fullcalendar/guides/custom-event-model). To learn how changes converge durably, see the [Persistence Model](/integrations/fullcalendar/concepts/persistence).

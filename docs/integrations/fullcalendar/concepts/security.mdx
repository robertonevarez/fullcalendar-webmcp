Protocol Tooling is an adapter between browser WebMCP agents and your calendar persistence. It does **not** authenticate users, store credentials, or authorize mutations. Your host application and backend remain authoritative.

## Security model

```text
User
  ↓ authenticated browser session
Host application
  ↓
WebMCP tools
  ↓
CalendarEventRepository
  ↓
Host backend / API
  ↓ server-side authorization
Persistence
```

WebMCP tools inherit the browser’s authenticated session ([WebMCP §6.2 — identity inheritance](https://webmachinelearning.github.io/webmcp/#agent-baseline-capabilities)). That inheritance enables agents to act on behalf of a logged-in user — it is **not** a substitute for checking permissions on every repository operation.

> **Tool discovery is not authorization.**

A tool being registered or callable must never be treated as proof that the current user may perform the underlying action. Authorization must occur on the authoritative backend/repository path — the same path your UI uses.

Examples:

- A user can view an event in the calendar but your API rejects updates → `calendar_update_event` must fail at the repository/backend, even if the tool is registered.
- An organization member must not access another tenant’s events → enforce tenant isolation server-side; hiding a tool in JavaScript is not sufficient.
- A read-only role must not mutate events because agent code can call registered tools → disable mutation capabilities **and** reject writes in the backend.

## Authentication

Protocol Tooling:

- Does **not** introduce login, OAuth, token storage, or a user model.
- Reuses your existing browser session and API authentication.
- Requires no Protocol Tooling–specific user account.

Your `CalendarEventRepository` implementation should call backend endpoints with the same cookies, headers, or tokens that ordinary application requests use. Backend endpoints must authenticate requests exactly as they would for non-agent interactions.

See also: [Repository contract](/integrations/fullcalendar/concepts/repository), [Persistence](/integrations/fullcalendar/concepts/persistence).

## Authorization

Every protected repository operation — `list`, `get`, `create`, `update`, `delete` — must ultimately be authorized by your backend or server-side logic.

UI permissions and WebMCP permissions must not diverge in a way that lets an agent bypass rules your UI enforces. If the UI hides a delete action, consider disabling the corresponding WebMCP capability (defense in depth) **and** rejecting unauthorized deletes in the repository.

When authorization fails, propagate the error from your repository. Protocol Tooling does not swallow host failures or convert them into apparent success, and it does not call `onEventsChanged` after a failed mutation.

## Capability exposure

`useFullCalendarWebMCP` accepts an optional `capabilities` object to control which tools are registered:

```ts
useFullCalendarWebMCP({
  calendarRef,
  events: repository,
  onEventsChanged: refreshEvents,
  capabilities: {
    read: true,
    create: true,
    update: true,
    delete: false, // calendar_delete_event is not registered
  },
});
```

| Capability | Tools affected when `false` |
|---|---|
| `read` | `calendar_list_events`, `calendar_get_event` |
| `create` | `calendar_create_event` |
| `update` | `calendar_update_event` |
| `delete` | `calendar_delete_event` |

Omitted capability fields default to enabled (preserves existing behavior).

`calendar_get_context` is **always** registered, even when `read: false`. It exposes viewport/timezone context generated by the library — not persisted event records — and helps agents interpret relative dates without listing events.

### Why expose fewer tools?

- **Least privilege** — reduce the agent’s callable surface to what the current user role needs.
- **Clearer planning** — agents only see tools that match UI capabilities.
- **Fewer accidental invocations** — mutation tools that are not registered cannot be called.

### What capability hiding is not

Browser-side tool hiding is **defense in depth**, not a security boundary. A determined client could still invoke your API directly. Server-side authorization remains mandatory.

The host application decides which capabilities a user receives (for example from session role, feature flags, or entitlements) and passes the matching `capabilities` configuration to the hook.

## Untrusted content and prompt injection

Event titles, host-selected metadata, and similar fields may contain adversarial text intended to manipulate agent behavior ([WebMCP §6.3.1 — prompt injection](https://webmachinelearning.github.io/webmcp/#prompt-injection-attacks), [Chrome secure tools guidance](https://developer.chrome.com/docs/ai/webmcp/secure-tools)).

Protocol Tooling applies WebMCP trust annotations per tool:

| Tool | `readOnlyHint` | `untrustedContentHint` | Rationale |
|---|---|---|---|
| `calendar_get_context` | `true` | default (`false`) | Library-generated viewport/time context |
| `calendar_list_events` | `true` | `true` | User-controlled titles and metadata |
| `calendar_get_event` | `true` | `true` | User-controlled titles and metadata |
| `calendar_create_event` | `false` | `true` | Mutation; returns persisted event fields |
| `calendar_update_event` | `false` | `true` | Mutation; returns persisted event fields |
| `calendar_delete_event` | `false` | default (`false`) | Structured confirmation, no free-text payload |

Per the [WebMCP specification §4.2.1](https://webmachinelearning.github.io/webmcp/#toolannotations), `untrustedContentHint` signals that output requires heightened client handling (for example spotlighting or sanitization). Annotations are behavioral hints for agents and user agents — not access controls.

These measures **reduce risk**; they do not eliminate prompt injection.

## Data minimization

Agent-visible event data is intentionally bounded:

- **Core fields only** on writes: `title`, `start`, `end`, `allDay`.
- **Metadata is opt-in** — optional `metadata?: JsonObject` on `CalendarEvent` reads.
- **Metadata is host-selected** — you project only what agents need.
- **Metadata is JSON-safe** — no `Date`, functions, or class instances.
- **Metadata is read-only at the WebMCP write boundary** — create/update schemas reject `metadata`.
- **No automatic `extendedProps` exposure** — FullCalendar extended properties are never serialized unless you explicitly map them into `metadata` in your repository.

### Do not

```ts
// ❌ Blindly spreading database records or extendedProps into agent-visible metadata
metadata: { ...dbRow, ...event.extendedProps }
```

Project only fields required for the agent task. Keep secrets, tenant identifiers, billing codes, and private notes out of `metadata`. See [Custom event model](/integrations/fullcalendar/guides/custom-event-model).

## Origin model

By default, WebMCP tools registered with `document.modelContext.registerTool` are available to **same-origin** agents only. Cross-origin documents and iframes cannot observe or invoke your tools unless you explicitly opt in ([WebMCP §4.2.3 — `exposedTo`](https://webmachinelearning.github.io/webmcp/#modelcontextregistertooloptions), [Chrome secure tools — expose carefully](https://developer.chrome.com/docs/ai/webmcp/secure-tools)).

Protocol Tooling does **not** pass `exposedTo` when registering tools. Cross-origin exposure requires explicit host action outside this library and carries significant security implications — especially for read tools (data disclosure) and write tools (actions on behalf of the user).

`document.modelContext` is a [Secure Context](https://webmachinelearning.github.io/webmcp/) API (HTTPS in production).

## Input validation at the WebMCP boundary

Tool `inputSchema` objects use JSON Schema with `additionalProperties: false`. Create/update schemas exclude `metadata`. Structural validation happens at the WebMCP boundary; business rules and authorization belong in your repository/backend.

Protocol Tooling does not invent a second validation layer for domain logic the backend already enforces.

## Host application checklist

Before production:

- [ ] Authenticate every backend request from your repository (same as non-agent traffic).
- [ ] Authorize every resource operation server-side.
- [ ] Enforce tenant/resource ownership and isolation.
- [ ] Expose only necessary WebMCP tools via `capabilities`.
- [ ] Expose only necessary fields in `metadata`.
- [ ] Validate mutation inputs in your API; reject malformed or unauthorized payloads.
- [ ] Use HTTPS in production (Secure Context requirement).
- [ ] Retain CSRF/origin protections appropriate to your architecture.
- [ ] Log or audit sensitive mutations where appropriate.
- [ ] Never place secrets, tokens, or private notes in agent-visible tool results.
- [ ] Unregister or disable tools when the user logs out (host responsibility — re-mount or gate registration on auth state).
